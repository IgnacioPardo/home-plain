# Architecture

The browser calls same-origin tRPC through `packages/client`. Hono constructs a PostgreSQL pool, `HomeStore` and authentication at startup. Environment is parsed only in `apps/api/src/env.ts`; the entrypoint initializes optional telemetry before importing modules that load HTTP or PostgreSQL.

PostgreSQL is the source of truth. `packages/backend/src/database/schema.ts` defines Drizzle tables. Versioned SQL and the migration journal live under `packages/backend/migrations`, are shipped with the package and run explicitly through `pnpm db:migrate`. The runner serializes concurrent migration commands with a PostgreSQL advisory lock. Update the schema and add a new SQL migration/journal entry together; do not edit an applied migration. Startup checks that the database has been initialized and fails closed if it is unavailable. `/health` is process liveness, not database readiness.

Households, users, memberships, rooms, purchases and feedback have relational columns and constraints. Catalog entries, documents and visual references retain validated JSONB content per individual record, scoped by a household key. JSONB preserves variable block/image metadata; it is not a runtime snapshot file. Imported source links remain attribution only. Existing document links can still resolve imported source IDs without contacting the original provider.

Every domain operation rechecks membership and scopes queries by household. The browser cannot supply a household or role for a mutation. Each account currently belongs to one household; bootstrap refuses to move an existing account or reset its credentials. Owner privileges permit purchase changes. Commenters may create feedback. Opaque server-side sessions, password hashing, host/origin checks and CSRF tokens protect the HTTP boundary. Session lookup refreshes roles and revokes access after password rotation or membership removal. Labels are not identity.

Purchase updates compare both status and a monotonically increasing integer version in one SQL UPDATE. Stale requests return a conflict; the UI reloads before another attempt. This works across independent API processes and catches a value changing away and back. Feedback uses a database unique constraint on `(household_id, operation_id)`, together with the authenticated author and a payload fingerprint, to return the original result on an identical retry and reject operation reuse with different content.

`importHome` validates a private bundle before one transaction, locks the destination household, and adds absent records. Repeating an import does not overwrite database edits. SQL failures roll back the entire bundle. The old JSON formats are accepted only at this explicit import boundary; runtime never reads them. Images stay under ignored `data/media`; an authenticated request can read only a file referenced by its household's catalog or moodboard. The frontend build contains no runtime records.

Sessions and login throttling remain in one API process and reset on restart. Data and credentials persist in PostgreSQL. Multiple API replicas require a shared session/throttling implementation; this release does not claim that capability. There is no automatic deployment, signup, invitation flow, or arbitrary purchase/document editor.

Transport and environment configuration stay in apps, domain behavior in the backend, and browser requests in query hooks. Zod validates import and API boundaries. Integration tests use real PostgreSQL, with a fresh schema per test, and cover atomic migration/import behavior, restart persistence, competing pools, idempotency and household authorization. UI tests cover error/loading states, retries, keyboard access and honest save confirmation.
